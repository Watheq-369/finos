# FinOS Backlog (living tracker)

The single place every discovery lands: blind spots, caveats, bugs, ideas, deviations, removals. From Younes, from Claude (chat), or from Claude Code during a build.

**The rule: if it is not in this file, it does not exist.** The moment something surfaces, it gets one line here. Reviewed at the start and end of every slice: what moved into scope, what got done, what is still parked.

**Where things live (so the backlog stays a tracker, not a dumping ground):**
- Permanent rules and principles go in `CLAUDE.md`.
- Scope for a slice goes in `docs/slice-N.md`.
- High-level state and decisions go in the project doc.
- Everything discovered-but-not-yet-placed goes here, tagged with where it belongs and a status.

Status tags: `[open]` `[in progress]` `[done]` `[dropped]`.

## Slice B1: real Stripe billing adapter (2026-08-15)

- `[done]` `invoiced_by` added to the `BillingClient` Protocol in `finos/interfaces.py`. It was called by `dedup.check_duplicate` but never declared, so any new billing client would have failed at runtime rather than at review time. Both `MockBilling` and `StripeBilling` now implement the same three-method shape, pinned by a test.
- `[done]` `StripeBilling` implements `BillingClient` against the real Stripe API. Finds or creates the customer, creates a DRAFT invoice for `invoice_amount` in the event currency, and never finalises or sends: `auto_advance=False`, and nothing in the file calls `finalize_invoice` or `send_invoice`.
- `[done]` Idempotency mirrors mock billing exactly. The event id and a `client|amount|currency` signature are written to Stripe invoice metadata (`finos_event_id`, `finos_signature`) and looked up before anything is created, so a second run returns the existing draft. A test asserts the Stripe and mock signature functions produce identical strings, because if those two ever drift one of them double-bills.
- `[decision]` Existing state is read with a plain `Invoice.list` / `Customer.list` at first use, NOT the Stripe Search API. Search is eventually consistent by up to a minute, so a pipeline re-run moments later could miss the invoice it just wrote and bill the client twice. Listing is immediately consistent. Cost: the listing is capped at the paging iterator and will get slower on a busy account; fine for test mode, revisit if the account grows.
- `[done]` **Hard stop on non-test keys.** `StripeBilling` refuses to construct unless the key starts with `rk_test_` or `sk_test_`. Billing a real client from a test run is the one mistake that cannot be undone, so this is an exception, not a warning. Covered by tests for live keys and for non-Stripe secrets.
- `[done]` Stripe is strictly opt-in behind `--stripe`, mirroring `--push`. `run_all(use_stripe=False)` is the default and `score.py` calls `run_all()` with no arguments, so the scorer and all 40 tests stay on `MockBilling` with no key and no network. A test asserts that default, so making Stripe the default would fail the suite.
- `[done]` The Stripe SDK is imported lazily inside `run_all`, not at module load, so a checkout without the `stripe` package can still run the whole offline suite. `stripe` added to `requirements.txt`.
- `[done]` A Stripe config failure prints a plain-language line and exits 1 instead of dumping a traceback, matching the existing `--push` failure handling. The case fired for real during this slice.
- `[open]` **BLOCKED: the live Stripe check could not be run.** The value in `STRIPE_RESTRICTED_KEY` is not a Stripe API key. It is 108 characters, base64-shaped (contains `=` padding and `_`), and matches none of Stripe's prefixes (`sk_test_`, `rk_test_`, `sk_live_`, `rk_live_`, `pk_`, `whsec_`). Stripe keys have no `=`. The guard refused to run, correctly, and nothing was transmitted. Deliberately did NOT attempt the call: sending an unidentified 108-char secret to Stripe would leak whatever service it actually belongs to. Needs a real restricted test-mode key (`rk_test_...`) from the Stripe dashboard, then re-run the two live checks.
- `[open]` `_minor_units` multiplies by 100, which is correct for EUR, USD and AED but wrong for zero-decimal currencies such as JPY and KRW (Stripe expects whole units there) and for three-decimal ones like BHD. The corpus contains none of these. Fix when a zero-decimal currency first appears, not before.
